# Дебаг за баг-репортом

## Роль

Досвідчений TypeScript-розробник, що діагностує production-інцидент: спершу
відтворює, потім пояснює причину, і лише тоді пропонує фікс.

## Мета

За описаним симптомом знайти точний root cause в `app/src/quote.ts`,
підтвердити його мінімальним відтворенням (repro), і закрити реґрес-тестом
+ мінімальним фіксом.

## Контекст

- Баг-репорт (від підтримки): «Клієнти повідомляють, що генератор кошторису
  іноді падає з помилкою на кшталт `RangeError: Invalid array length` при
  спробі розбити суму на платежі. Буває також, що платіжний план виходить
  порожнім при ненульовій сумі — без помилки, але явно неправильно.»
- Файли: `app/src/quote.ts` (`splitInstallments`), `app/src/quote.test.ts`.
- Команда тестів: `cd app && npm test`; typecheck: `cd app && npm run typecheck`.

## Обмеження

- Спочатку відтвори баг (конкретний вхід, що ламається) — тільки потім
  виправляй. Не пропонуй фікс без підтвердженого repro.
- Diff обмежений `app/src/quote.ts` і `app/src/quote.test.ts`.
- Не змінюй публічний тип повернення `splitInstallments` (масив чисел); можна
  додати явну валідацію вхідних параметрів, яка кидає зрозумілу помилку.
- Не чіпай `estimateTotalCents` і `formatMoney`, якщо баг-репорт їх не стосується.
- Поведінка для всіх уже існуючих (валідних) вхідних даних має лишитись
  незмінною — існуючі тести не повинні почервоніти.

## Acceptance criteria

- [ ] Наведено конкретний вхід(и), що відтворює(ють) кожен із двох описаних
      симптомів (крах і мовчазний порожній результат).
- [ ] Пояснено root cause: чому саме такий вхід ламає функцію (не просто
      «баг у splitInstallments», а конкретний рядок і механізм).
- [ ] Додано валідацію: `parts` має бути цілим додатним числом; невалідний
      вхід кидає явну, зрозумілу помилку (не `RangeError: Invalid array length`
      з внутрішнього `new Array()`).
- [ ] Додано реґрес-тести на обидва симптоми (дробове `parts`, `parts <= 0`).
- [ ] `cd app && npm test` — 0 failing; `npm run typecheck` — без помилок.
- [ ] Наявні тести (валідні входи) не змінені й не почервоніли.

## Формат відповіді

1. Repro: `вхід → що відбувається зараз` для кожного симптому.
2. Root cause (1–3 речення на симптом, з посиланням на файл:рядок).
3. Diff (валідація + тести).
4. Підсумок: passed/failed до і після.

## Stop

Після зелених тестів на обидва симптоми — зупинись. Не переписуй решту
файлу і не додавай валідацію для параметрів, не згаданих у баг-репорті.

## Нотатки із запуску (доказ, що промпт працював)

**Repro, перевірено вручну перед запуском промпту** (щоб мати незалежне
підтвердження симптому, а не вірити агенту на слово):

```
splitInstallments(1000, 2.5)  → CRASH: "Invalid array length"
splitInstallments(1000, -3)   → CRASH: "Invalid array length"
splitInstallments(1000, 0)    → [] (мовчазна втрата суми, без помилки)
```

**Запуск промпту** (окремий агент, без доступу до цього нотатника — лише
баг-репорт і код): root cause визначено як відсутність валідації `parts` у
`splitInstallments` — `new Array(parts)` кидає нативний `RangeError`, коли
`parts` не є невід'ємним цілим у межах ліміту рушія, а `parts <= 0` дає
`Array(0..).fill(...)`, тобто порожній/некоректний масив без сигналу про
помилку.

**Фікс:** на початку `splitInstallments` додано перевірку
`Number.isInteger(parts) && parts > 0`, інакше кидається
`new Error("parts must be a positive integer")`. Для валідних входів
поведінка не змінилась (перевірено — усі 19 наявних тестів лишились
зеленими).

**Нові тести:** `parts = 2.5` → кидає помилку; `parts = 0` → кидає помилку;
`parts = -3` → кидає помилку; є явний "щасливий" тест, що валідний виклик
(`parts = 3`, ціле додатне) як і раніше повертає масив без помилки.

**Після:** `cd app && npm test` — **22 passed, 0 failing**;
`npm run typecheck` — без помилок.

**Чому це окремий промпт, а не частина `add-tests.md`:** інший клас дефекту
(відсутня вхідна валідація й контрольований крах — не помилка округлення) і
інший workflow (спочатку repro за баг-репортом, а не «додай тести й полагодь,
що знайдеш»). Розділення тримає «один промпт — одна задача» (правило
бібліотеки, `prompts/README.md`).

## Той самий промпт у XML-діалекті

Той самий баг-репорт, ті самі acceptance criteria — лише формат (щоб
порівняння діалектів було чесним: різний формат тієї самої задачі, а не
дві різні задачі).

```xml
<task>Дебаг за баг-репортом: root cause + реґрес-тест</task>
<role>Досвідчений TypeScript-розробник, що діагностує production-інцидент: спершу відтворює, потім пояснює причину, і лише тоді пропонує фікс</role>
<context>
  <domain>Кошториси; суми — цілі центи</domain>
  <files>app/src/quote.ts, app/src/quote.test.ts</files>
  <tests>cd app &amp;&amp; npm test</tests>
  <typecheck>cd app &amp;&amp; npm run typecheck</typecheck>
  <bug_report>
    Клієнти повідомляють, що генератор кошторису іноді падає з помилкою на
    кшталт RangeError: Invalid array length при спробі розбити суму на
    платежі. Буває також, що платіжний план виходить порожнім при
    ненульовій сумі — без помилки, але явно неправильно.
  </bug_report>
</context>
<constraints>
  <require>спершу repro (конкретний вхід, що ламається), лише потім фікс</require>
  <scope_limit>app/src/quote.ts, app/src/quote.test.ts</scope_limit>
  <no>змінювати публічний тип повернення splitInstallments</no>
  <no>чіпати estimateTotalCents/formatMoney, якщо репорт їх не стосується</no>
  <require>поведінка для всіх уже існуючих валідних входів лишається незмінною</require>

<acceptance>
  <item>конкретний вхід, що відтворює кожен із двох симптомів (крах і мовчазний порожній результат)</item>
  <item>root cause із посиланням на файл:рядок для кожного симптому</item>
  <item>валідація: parts має бути цілим додатним числом, невалідний вхід кидає явну помилку (не RangeError з new Array())</item>
  <item>реґрес-тести на обидва симптоми (дробове parts, parts &lt;= 0)</item>
  <item>наявні тести (валідні входи) не змінені й не почервоніли</item>

<stop>Після зелених тестів на обидва симптоми — зупинись; не додавай валідацію для параметрів, не згаданих у баг-репорті</stop>
```

### Чи відчув я різницю між діалектами (чесно, за реальним прогоном)

Прогнав обидва варіанти (markdown і XML вище) як два незалежні **сухі
прогони** (аналіз і пропонований diff, без запису на диск) над одним і тим
самим баг-репортом («крах на невалідному `parts`» + «мовчазний порожній
план при `parts = 0`»), щоб порівняти чесно, без різниці у задачі.

На момент цього конкретного прогону `app/src/quote.ts` вже містив фікс із
першого, реального запуску цього промпту (див. «Нотатки із запуску»
вище) — тож обидва діалекти, замість пропонувати diff, **чесно
відповіли, що баг-репорт більше не відтворюється**, процитувавши конкретні
рядки (`app/src/quote.ts:75-79`) і наявні реґрес-тести
(`app/src/quote.test.ts:99-129`), а не вигадали проблему заради
демонстрації. Обидва відмовились пропонувати diff, пославшись на власне
`<stop>`-правило («не додавай валідацію для параметрів, не згаданих у
баг-репорті»). Різниці в діагнозі, повноті чи рішенні між діалектами не
було — обидва дійшли того самого висновку тими самими цитатами з коду.

**Висновок:** для цього конкретного, уже добре структурованого промпту
діалект не вплинув на якість чи повноту діагнозу — лише на дрібниці форми
відповіді (XML тримав трохи чіткіший поділ repro/root cause/diff по
тегах). Ще важливіше: обидва діалекти показали одну й ту саму корисну
властивість — промпт з чіткими acceptance criteria не змушує агента
«знайти» неіснуючу проблему, коли її вже немає; він чесно каже «нічого
виправляти».

### Друга ітерація: той самий промпт, інший баг-репорт

Пізніше, коли `prompts/review-changes.md` (рев'ю кумулятивного дифу)
знайшов ще два реальні дефекти в тому самому `splitInstallments` —
відсутню верхню межу на `parts` (падіння на надмірно великих значеннях) і
невалідований дробовий `totalCents` — цей самий шаблон промпту (Роль/Мета/
Контекст/Обмеження/Acceptance/Формат/Stop) застосовано ще раз, із новим
баг-репортом під ці два симптоми. Це **не другий діалект**, а повторне
використання того самого промпт-паттерну на новій задачі — тому оформлено
окремо, а не як частина пари «MD vs XML» вище, щоб не змішувати «різний
формат тієї самої задачі» з «той самий формат іншої задачі».

Обидва (MD і XML) варіанти цієї другої задачі незалежно знайшли той самий
root cause (`app/src/quote.ts` — відсутня верхня межа на `parts` і
відсутня перевірка цілочисельності `totalCents`) і запропонували
структурно ідентичний фікс, з єдиною різницею — MD запропонував
`MAX_INSTALLMENTS = 1_000_000`, а варіант з іншим форматом — `100_000`
(обидва довільні, реальний ліміт вартий обговорення з командою). Фактично
застосовано `100_000` (консервативніший з двох) — див. `app/src/quote.ts`
і `docs/injection-report.md`/`prompts/review-changes.md` для контексту,
де саме цю знахідку зафіксовано й закрито.
