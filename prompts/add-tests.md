# Додавання тестів на крайові випадки

## Роль

Senior TypeScript-розробник, що пише production-код з тестами для фінансових
розрахунків (гроші — цілі числа в центах, без float-похибок) і виправляє
дефекти, які тести виявляють — а не підлаштовує тести під баговану поведінку.

## Мета

Довести test coverage `app/src/quote.ts` до повністю зеленого стану,
**виправивши причину дефекту в реалізації**, і додати тести на крайові
випадки, яких зараз бракує.

## Контекст

- Файли: `app/src/quote.ts` (реалізація: `estimateTotalCents`,
  `splitInstallments`, `formatMoney`), `app/src/quote.test.ts` (тести).
- У `quote.test.ts` уже є два тести, позначені коментарем `ДЕФЕКТ`
  (~рядки 50–62), які зараз **FAIL** і документують відомий баг:
  `splitInstallments` округлює кожен платіж незалежно, тому сума елементів
  масиву може не дорівнювати `totalCents`.
- Команда тестів: `cd app && npm test`; typecheck: `cd app && npm run typecheck`.

## Обмеження

- Diff обмежений лише `app/src/quote.ts` і `app/src/quote.test.ts` — не
  чіпати конфігурацію (`package.json`, `tsconfig.json`, vitest-конфіг) і не
  додавати залежностей.
- Публічні сигнатури `estimateTotalCents`, `splitInstallments`, `formatMoney`
  незмінні.
- Тести, позначені коментарем `ДЕФЕКТ`, **не можна** видаляти, скіпати
  (`it.skip`/`xit`) чи послаблювати (змінювати очікуване значення під
  поточну баговану поведінку) — вони мають пройти через виправлення
  `splitInstallments`, а не через зміну очікувань.
- Жоден раніше зелений тест не повинен стати червоним і не повинен бути
  видалений.
- Заборонено досягати «зелених тестів» через `.skip`/`.only`, які лишаються
  в коді, глушіння помилок (порожні try/catch), `@ts-ignore`/`any`.

## Acceptance criteria

- [ ] Дефект округлення в `splitInstallments` виправлено так, що сума
      елементів масиву завжди дорівнює `totalCents` (для будь-якого ділення,
      з остачею чи без).
- [ ] Обидва наявні тести з коментарем `ДЕФЕКТ` проходять **без зміни**
      очікуваних значень.
- [ ] Додано щонайменше 3 нові тести на крайові випадки, яких не було
      раніше (напр.: `parts` більший за `totalCents`, від'ємний `totalCents`,
      детермінований розподіл залишку по копійках).
- [ ] `cd app && npm test` — 0 failing, і в коді не лишилось `.skip`/`.only`.
- [ ] `cd app && npm run typecheck` проходить без помилок.
- [ ] Жоден наявний тест-кейс (за назвою) не видалений — якщо структура
      `describe`/`it` змінилась, дай список «до/після».

## Формат відповіді

1. Список знайдених дефектів: `файл:рядок | вхід | наслідок`.
2. Diff, обмежений `app/src/quote.ts` і `app/src/quote.test.ts`.
3. Коротке (2–4 речення) пояснення причини дефекту й підходу до фіксу.
4. Підсумок запуску тестів: passed/failed до і після, typecheck.

## Stop

Коли (1) `npm test` повністю зелений, (2) обидва `ДЕФЕКТ`-тести пройшли без
послаблення очікувань, (3) жоден наявний тест не видалений/вимкнений — зупинись
і чекай на рев'ю. Не додавай нових публічних функцій чи валідації вхідних
даних поза межами виправлення дефекту.

## Meta-prompting (крок 3 з walkthrough)

Перед фінальним запуском попросив агента покритикувати чернетку промпту
(v1, без явних заборон на «маніпуляцію тестами»). Ключова знахідка критики:
чернетка була internally суперечливою — вимагала одночасно «не ламай існуючі
тести» і «npm test проходить», а два наявні тести на дефект вже були
червоними. Найлегший шлях задовольнити обидві вимоги — **послабити або
видалити ці два тести**, а не виправити `splitInstallments`. Агент також
вказав на відсутність: заборони на `.skip`/`.only`/глушіння помилок,
обмеження diff двома файлами, і вимоги показати список тест-кейсів «до/після».
Усе це додано у v2 вище (розділи Обмеження + Acceptance criteria).

## Нотатки із запуску (доказ, що промпт працював)

**До:** `npm test` — 16 тестів, **2 failing** (обидва в `splitInstallments`,
рядки 50 і 61 в `quote.test.ts`): `expected 99 to be 100` і
`expected 9999 to be 10000`.

**Знайдений дефект:** `app/src/quote.ts` (стара версія, `splitInstallments`)
— округлював **кожен** платіж незалежно (`Math.round(totalCents / parts)`
для всіх `parts` елементів), тому сума масиву могла не збігатися з
`totalCents` при недільному діленні.

**Фікс:** переписано на цілочисельний розподіл із залишком —
`base = Math.trunc(totalCents / parts)`, різниця
`totalCents - base * parts` розкидається по перших N платежах (по 1 центу,
зі знаком). Публічна сигнатура не змінилась.

**Нові тести додано** (`splitInstallments`): детермінований розподіл
залишку (`100, 3` → `[34, 33, 33]`); `parts` більший за `totalCents`
(`2, 5` → `[1, 1, 0, 0, 0]`); від'ємна сума (повернення коштів).

**Після:** `npm test` — 19 тестів, **0 failing**; обидва `ДЕФЕКТ`-тести
пройшли без зміни очікувань. `npm run typecheck` — без помилок.

**Порівняння з weak-prompt baseline:** цей самий репозиторій вже містить
`AGENTS.md`, тож слабкий промпт («допоможи з тестами для app») у нашому
запуску не «розповзся» хаотично — агент прочитав `AGENTS.md`, зрозумів, що
дефект це частина завдання, і зупинився на самому лише звіті, не
торкнувшись коду (жодних змін файлів). Це саме по собі демонструє
проблему слабкого промпту: без явних acceptance criteria агент **сам
вирішив** межі задачі й критерій «готово» — в кращому випадку зупинився
надто рано (нічого не полагодив), в гіршому — на репо без `AGENTS.md` міг
би або нічого не знайти, або почати правити довільні файли. Промпт
`add-tests.md` (v2) прибирає цю невизначеність: конкретний файл, конкретний
дефект, заборона на «дешеві» шляхи до зелених тестів.
