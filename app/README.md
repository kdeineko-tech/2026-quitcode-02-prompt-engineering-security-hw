# app — quote calculator

Документація публічного API модуля `src/quote.ts`: розрахунок кошторису
проєкту, розбиття суми на платежі та форматування грошових сум.

Усі три функції — чисті (без побічних ефектів, не змінюють вхідні дані).
Усі грошові суми в API — **цілі центи** (`number`, ціле значення), а не
долари/float. Це навмисний вибір: арифметика з плаваючою комою (`float`) не
може точно представити частки долара (наприклад, `0.1 + 0.2 !== 0.3`), тому
всі суми в межах модуля рахуються в найменшій неподільній одиниці (центах) і
округлюються до цілого один раз — на виході кожної функції, а не
накопичувально під час обчислень.

Джерело істини для поведінки на межових випадках — `src/quote.test.ts`
(23 тести, усі проходять: `npm test`).

## `estimateTotalCents`

```ts
function estimateTotalCents(input: QuoteInput): number
```

```ts
interface QuoteInput {
  hours: number;          // оцінка робіт у годинах
  rateCents: number;      // ставка за годину, у центах (напр. 5000 = $50.00)
  discountPercent?: number; // знижка у відсотках, 0..100; за замовчуванням 0
}
```

Рахує вартість проєкту в центах: `hours * rateCents`, зменшену на
`discountPercent` відсотків, і округлює результат до найближчого цілого
центу (`Math.round`).

Приклад (перевірено — `npx vitest run`, значення співпадають з
`src/quote.test.ts`):

```ts
estimateTotalCents({ hours: 10, rateCents: 5000 });
// -> 50000  (10 год * $50.00 = $500.00, без знижки)

estimateTotalCents({ hours: 10, rateCents: 5000, discountPercent: 10 });
// -> 45000  ($500.00 - 10% = $450.00)

estimateTotalCents({ hours: 10, rateCents: 999, discountPercent: 33 });
// -> 6693   (10 * 999 = 9990; знижка 33% -> 9990 - 3296.7 = 6693.3 -> округлення -> 6693)
```

### Нестандартна поведінка

- `discountPercent` не валідується: значення поза діапазоном `0..100`
  (наприклад, `-10` або `150`) не кидають помилку — функція просто
  застосує їх буквально (від'ємна знижка збільшить суму, знижка > 100%
  дасть від'ємний результат).
- `hours` може бути дробовим (`2.5`) — це підтримується і не є помилкою.
- Округлення (`Math.round`) відбувається один раз, після застосування
  знижки, — не окремо для `gross` і `discount`.

## `splitInstallments`

```ts
function splitInstallments(totalCents: number, parts: number): number[]
```

Розбиває `totalCents` на `parts` платежів так, щоб **сума елементів масиву
завжди точно дорівнювала `totalCents`** (без втрати чи появи центів через
округлення). Базовий платіж — `Math.trunc(totalCents / parts)`; залишок від
цілочисельного ділення розподіляється по одному центу, починаючи з перших
платежів масиву (детерміновано: однакові аргументи завжди дають однаковий
результат).

Приклад (перевірено — `npx vitest run`):

```ts
splitInstallments(90000, 3);
// -> [30000, 30000, 30000]   (ділиться націло)

splitInstallments(10, 4);
// -> [3, 3, 2, 2]
// 10 / 4 = 2.5 -> база 2, залишок 2 центи -> перші 2 платежі отримують +1

splitInstallments(-100, 3);
// -> [-34, -33, -33]
// від'ємні суми теж підтримуються; сума масиву = -100
```

### Обмеження і крайові випадки — обов'язково прочитати

`parts` **має бути цілим додатним числом** (`Number.isInteger(parts) &&
parts > 0`). Якщо ні — функція кидає `Error` (а не повертає `NaN`, `[]` чи
не падає з незрозумілим `RangeError`, як робила попередня реалізація):

```ts
splitInstallments(100, 2.5);
// -> throws Error: splitInstallments: "parts" must be a positive integer, отримано 2.5

splitInstallments(100, -2);
// -> throws Error: splitInstallments: "parts" must be a positive integer, отримано -2

splitInstallments(100, 0);
// -> throws Error: splitInstallments: "parts" must be a positive integer, отримано 0

splitInstallments(100, Number.NaN);
// -> throws Error: splitInstallments: "parts" must be a positive integer, отримано NaN
```

Отже: дробове (`2.5`), від'ємне (`-2`), нульове (`0`), `NaN` чи **надмірно
велике** (> 100 000, див. нижче) значення `parts` завжди кидає помилку з
повідомленням, що містить слово `parts` — на це можна покластися при
написанні `try/catch` чи `expect(...).toThrow(/parts/i)`.

`parts` також має **верхню межу — 100 000**. Значення вище цього ліміту
кидають ту саму зрозумілу помилку валідації, а не нативний
`RangeError: Invalid array length` чи вичерпання пам'яті:

```ts
splitInstallments(100, 5_000_000_000);
// -> throws Error: splitInstallments: "parts" перевищує допустиму межу (100000), отримано 5000000000
```

`totalCents` **має бути цілим числом** (центи). Дробове значення теж
відхиляється помилкою — інакше сума платежів мовчки розходилася б із
вихідною сумою:

```ts
splitInstallments(100.5, 3);
// -> throws Error: splitInstallments: "totalCents" must be an integer number of cents, отримано 100.5
```

Інші нюанси:

- `parts` може бути **більшим за `totalCents`** (але в межах ліміту
  100 000) — це не помилка. Наприклад, `splitInstallments(100, 250)`
  поверне масив довжиною 250, де перші 100 елементів дорівнюють `1`, а
  решта — `0`.
- `totalCents` може бути **від'ємним** — розподіл залишку працює
  симетрично (перші платежі зменшуються на 1 цент замість збільшення).

## `formatMoney`

```ts
function formatMoney(cents: number): string
```

Форматує цілі центи у рядок вигляду `"$1,234.50"`: розділювач тисяч через
кому, завжди дві знаки після коми, знак `-` перед `$` для від'ємних сум.

Приклад (перевірено — `npx vitest run`):

```ts
formatMoney(123450); // -> "$1,234.50"
formatMoney(0);       // -> "$0.00"
formatMoney(-500);    // -> "-$5.00"   (знак перед "$", а не перед числом)
formatMoney(105);     // -> "$1.05"    (дробова частина доповнюється нулем зліва)
```

### Нестандартна поведінка

- Знак `-` ставиться перед `$`, а не перед числом (`"-$5.00"`, не
  `"$-5.00"`).
- Дробові (нецілі) `cents` не валідуються — функція очікує ціле число
  центів; на дробовому вході результат не визначений цим модулем.
- Формат тисячних розділювачів фіксований на локалі `"en-US"`
  (`toLocaleString("en-US")`) незалежно від системної локалі виклику.

## Обмеження і крайові випадки (зведення)

- **Усі суми — цілі центи**, ніколи не долари/float. Це усуває похибки
  накопичення плаваючої коми (`0.1 + 0.2 !== 0.3`); округлення до цілого
  центу відбувається один раз, на виході функції.
- `estimateTotalCents` не валідує `discountPercent` за межами `0..100` —
  виклик з некоректним відсотком не впаде, але дасть математично
  "неправильний" (від'ємний або завищений) результат без попередження.
- `splitInstallments` **кидає `Error`**, якщо `parts` не є цілим додатним
  числом у межах 100 000 (нецілі, від'ємні, нуль, `NaN`, надмірно великі) —
  повідомлення завжди містить слово `parts`. Це навмисна заміна попередньої
  поведінки, коли такі входи або кидали непрозорий `RangeError`
  (`new Array(parts)` з невалідною довжиною чи вичерпанням пам'яті), або
  мовчки повертали порожній/некоректний план платежів.
- `splitInstallments` **кидає `Error`**, якщо `totalCents` не є цілим
  числом — інакше сума елементів результату мовчки розходилась би з
  вихідною сумою через дробовий залишок.
- `splitInstallments` коректно обробляє `parts > totalCents` (у межах
  ліміту) та від'ємний `totalCents` — сума елементів результату завжди
  точно дорівнює `totalCents`.
- `formatMoney` не валідує вхід і не кидає помилок — вона довіряє, що на
  вхід подають цілі центи.
- Усі приклади в цьому README відповідають тестам у `src/quote.test.ts` і
  фактично виконані через `npx vitest run` (23/23 тести проходять на
  момент написання документа).
