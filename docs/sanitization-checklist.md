# Чек-ліст санітизації даних для роботи з AI

> Багаторазовий документ команди — перед тим, як вставити будь-який
> клієнтський матеріал (бриф, лист, вигрузку, тікет) у чат з AI-моделлю,
> пройдіть ці кроки. Ціль — щоб задача лишалась зрозумілою моделі, а
> нічого зайвого не поїхало в модель.

## 1. Що шукаємо (світлофор)

| Категорія | Приклади | Куди можна |
|---|---|---|
| 🔴 Секрети | API-ключі, токени, connection strings, паролі, n8n credentials | нікуди; лише out-of-band через env на етапі запуску |
| 🔴 PII клієнтів | ПІБ, email, телефон, адреса, месенджери (особисті, не робочі канали) | нікуди в **жодну** AI-модель (публічну чи enterprise) — обробка лише в контрольованій CRM/системі або через маскування перед тим, як щось іде в модель |
| 🔴 Продакшн-дані | вигрузки таблиць, логи з даними користувачів, реальні замовлення | нікуди; замінити синтетикою того самого формату |
| 🟡 Внутрішня комерція | ставки, собівартість, маржа, умови угод, конкурентна ситуація, дедлайни переговорів | лише enterprise-тір з no-train / zero data retention (див. розділ 4) |
| 🟡 Внутрішня логіка | назви внутрішніх систем, схеми БД, назви гілок/репозиторіїв, внутрішні процеси | лише enterprise-тір з no-train (див. розділ 4) |
| 🟢 Постановка задачі | опис проблеми, критерії приймання, обсяги без даних, технологічний стек | будь-яка модель, включно з публічною |

**Як розпізнати категорію швидко:** якщо видалення значення з документа не
заважає зрозуміти, ЩО треба зробити — це, ймовірно, 🔴 чи 🟡 (дані, а не
задача). Якщо видалення ламає розуміння задачі — це, ймовірно, 🟢
(постановка), і видаляти нема чого.

## 2. Як маскуємо

| Техніка | Коли застосовувати | Приклад |
|---|---|---|
| **redaction** — прибрати повністю | Дані, які взагалі не потрібні моделі для розуміння задачі (особисті месенджери, зайві деталі) | `<REMOVED>` |
| **masking** — лишити форму, прибрати значення | Коли модель має розуміти *формат* поля (номер телефону, останні цифри картки) | `+380 (XX) XXX-XX-XX`, `****-1234` |
| **synthetic** — замінити правдоподібним вигаданим | Коли модель має бачити *приклад* реалістичних даних (вигрузка, тестові рядки), але не справжні значення | `[CLIENT_1]`, `orders@example.test` |
| **out-of-band** — секрет не потрапляє в текст узагалі | Будь-які креденшели: ключі, токени, паролі, connection strings | `<SECRET_OUT_OF_BAND>` (реальне значення передається лише через env на етапі запуску, ніколи в промпт чи документ) |
| **internal placeholder** — прибрати внутрішньокомерційне число, лишивши факт, що воно є | Ставки, маржа, собівартість, комерційний контекст | `<INTERNAL>` |

**Головне правило:** після маскування задача має лишитись зрозумілою. Якщо
модель більше не розуміє, що робити — ви замаскували зайве (санітизація
«під нуль»). Перевірка: прочитайте санітизований документ так, ніби ви і є
модель, — чи можете ви сформулювати план дій без жодного реального
значення?

## 3. Перед тим, як вставити в модель

- [ ] Пройшов пошуком по: `key`, `token`, `secret`, `password`, `postgres://`,
      `xoxb-`, `@` (email/handle), `+380` чи інший формат телефону
- [ ] Немає жодного справжнього телефону / email / ПІБ / месенджера
- [ ] Немає справжньої назви компанії клієнта (замінено на `[CLIENT_1]`
      тощо) — назва сама по собі часто ідентифікує клієнта не гірше за ПІБ
- [ ] Вигрузки й приклади даних замінені синтетичними рядками того самого
      формату (та сама кількість колонок, той самий тип значень)
- [ ] Секрети — лише через env на етапі запуску, не в промпті й не у файлі,
      який піде в модель
- [ ] Внутрішньокомерційні числа (ставки, маржа, собівартість) прибрані або
      позначені `<INTERNAL>`
- [ ] Перечитав результат як «свіжа людина без контексту» — задача досі
      зрозуміла без реальних даних
- [ ] Обраний інструмент/тір відповідає **найвищій** категорії, що лишилась
      у документі (якщо лишився хоч один 🟡 пункт — весь документ вимагає
      🟡-тіру, не 🟢)

## 4. Інструмент під категорію

| Категорія | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | Будь-яка модель, включно зі звичайною споживчою підпискою | Дані відсутні за визначенням — ризик витоку не залежить від тіру моделі |
| 🟡 | Enterprise-тір з контрактним no-train / zero data retention (напр. Team/Enterprise-план з підписаним DPA), АБО локальна модель у контурі компанії, якщо контракту з вендором немає | Внутрішня комерція й логіка не є персональними даними, але їх витік шкодить бізнесу (конкурент бачить маржу, дедлайни); no-train контракт знімає ризик потрапляння в тренувальні дані, а не лише «обіцянку не читати» |
| 🔴 | AI взагалі не використовуємо на цих даних | Секрети й PII — не питання «якого тіру модель», а питання, чи цим даним взагалі місце поза захищеним сховищем секретів / CRM з контролем доступу |

## 5. Один параграф: який тір/інструмент для 🟡-даних і чому

Для 🟡-даних (внутрішня комерція, внутрішня логіка) команда використовує
**enterprise-підписку з контрактним no-train / zero data retention**, а не
локальну модель за замовчуванням. Причина: локальна модель знімає ризик
витоку за межі компанії повністю, але для невеликої агенції утримання
власної інфраструктури (GPU, оновлення, безпека) дорожче й повільніше, ніж
контрактна гарантія від вендора — а enterprise-тір з підписаним DPA і
no-train умовою дає порівнянний рівень захисту (дані не йдуть у тренувальні
вибірки, зберігання обмежене за часом) при значно нижчій вартості
володіння. Локальну модель варто розглядати окремо, якщо клієнт має власну
жорстку комплаєнс-вимогу (напр. дані не можуть покидати визначений периметр
взагалі) — тоді 🟡-дані цього конкретного клієнта переводяться в режим 🔴
на час роботи з ним, і рішення приймається окремо для цього кейсу, а не як
загальне правило команди.
